# Chapter annotation backend contract

Integration target: current DualQuill0.4.28. Backend only; no version bump, frontend changes, tests, real-provider calls, or schema upgrade performed. Source review is not runtime validation; coordinator must integrate/build before release.

## HTTP and common fields

Base: `/api/projects/{project}/annotations`. Existing localhost/origin/session-token protections apply. Every POST requires `Content-Type: application/json` and `X-Novel-Token`. All mutations require `operation_id` (canonical UUID string) and `expected_revision` (strict integer, not boolean). Unknown fields are rejected. POST payload maximum remains the server's 12 MiB, with the annotation-specific serialized limit of 1,000,000 characters.

`GET base` returns `{revision, annotations:[Annotation], coordinates:"Unicode code points; end exclusive", model_request_sent:false}`. `GET base/{id}` returns `{revision, annotation:Annotation}`. Neither starts generation, provider checks, or network requests.

`POST base` creates an annotation and returns HTTP 201 with `{revision, annotation}`. Required fields, in addition to the common fields: `chapter_id`, `version_id`, `body_sha256`, `start`, `end`, `quote`, `instruction`, `kind`. `kind` is `comment`, `replace`, or `delete`. `version_id` is the current saved chapter version. `body_sha256` is the lowercase SHA-256 of the exact whole chapter encoded as UTF-8. `start` and `end` are strict integer Unicode codepoint offsets, end exclusive; JavaScript callers must convert UTF-16 offsets (for example via Array.from), not send DOM code-unit offsets. `quote` must equal the exact saved `body[start:end]`. Whole chapter means start 0, end codepoint length, and quote equal to the whole body. Nonempty chapters require a nonempty selection. Empty saved chapters permit 0:0. Instruction whitespace and line breaks are preserved, with a nonempty trimmed check, maximum 12,000 characters. Body/quote/candidate full-body maximum is 200,000 characters. NUL and invalid Unicode encoding are rejected. Source project/chapter membership, activity, hidden/archive/trash state, current version and whole-body hash are checked; no substring reanchoring occurs.

Metadata edits do not increment workspace revision. Use the returned current workspace revision for subsequent actions. Existing operation IDs replay the current annotation projection without repeating side effects; reuse with a different route/action/payload, including a changed expected_revision, is rejected. Retain and resend the identical original payload after a lost response. Replays are scoped to a project. Maximum 10,000 retained operation receipts per project, 100 history entries per annotation; limits reject rather than silently evict idempotency receipts.

## Actions

`POST base/{id}/{action}` returns `{revision, annotation}`. Common fields are always required. Additional exact fields:

| Action | Additional required fields | Optional fields | Effect |
| --- | --- | --- | --- |
| update-note | instruction | none | Preserve original instruction, update current instruction, invalidate review/request preparation. |
| manual-candidate | replacement | none | Store exact replacement, invalidate review, no model call. Not available for comment. Delete accepts only empty replacement. |
| generate | none when preparing | confirm_external, request_sha256 | Two-phase direct replacement generation; see below. Not available for comment/delete. |
| review | none when preparing | confirm_external, request_sha256 | Two-phase independent audit of exact candidate full-body. Candidate required. |
| accept | confirmed, candidate_sha256, review_choice | authorize_confirmed | Explicit author body save. confirmed must be true; SHA-256 binds exact replacement. review_choice is reviewed or unchecked. |
| undo | confirmed | authorize_confirmed | Restore exact pre-accept source body as a new business-save version, only if accepted after version AND hash are still current. |
| cancel | none | none | Signal the current annotation job; preserve candidate and body. No body undo. A strict integer expected_revision is required but may be stale; cancellation remains available after source changes or archival. |
| discard | none | none | Mark metadata discarded. Never delete body. Accepted annotations must be undone before discard. |
| reconcile | confirmed, resolution, observed_version_id, observed_body_sha256 | none | Explicit pending-intent recovery, never body replay. |

`authorize_confirmed` is a strict boolean defaulting to false and is supplied only by an explicit author decision. Confirmed chapters are not automatically unlocked. Existing body-range, plan/formal and repository guards remain in force. `accept` permits reviewed failed candidates only through the author's explicit reviewed choice; that choice never changes the actual verdict. `unchecked` also never changes an unverified/failed review into passed. A reviewed choice requires a verified report bound to the exact replacement hash. A no-op body replacement is rejected.

## Generation/review flow

1. POST generate or review with only the common fields. HTTP 202 returns a prepared request, but sends nothing. `annotation.prepared_request` includes `action`, `revision`, `request_sha256`, `writer_destination`, `reviewer_destination`, `tokens`, `created_at`, exact `messages`, and unknown-cost notice. Destinations contain credential-free connection ID, revision, protocol, base URL, local scope and SHA-256. The selected target is writer_destination for generate and reviewer_destination for review.
2. Show the exact request/context, destination and unknown cost to the author. POST the same action with a NEW operation_id, current expected_revision, `confirm_external:true`, and the exact prepared `request_sha256`.
3. Poll GET detail. Execution is background/nonblocking. `annotation.job` contains id, action, request_sha256, status, timestamps, error. Status is running, cancelling, succeeded, failed, stale, cancelled, or projected interrupted after process restart. No automatic resubmission occurs. Retry requires new preparation and new explicit confirmation; each prepared request is single-use.
4. Preview candidate and independently invoke review if desired. Neither generation nor review autoapplies a body.
5. Explicitly accept, then use returned workspace revision to refresh the editor.

Writer and reviewer settings are frozen from actual existing ChatAgent settings, including reviewer selection policy, selected skills and transport configuration. Review requires a distinct connection AND a distinct (base URL, model) pair. Both saved connections must be available even when only generating. Model session enabled/offline, connection enabled/revision/model/protocol/destination, skills manifest, project activity, workspace revision and source binding are checked before requests and before publishing results. Existing ChatAgent HTTP transport, cancellation watcher, endpoint validation and provider reservation are reused; planner and tool dispatch are never invoked. Exactly one request attempt, 180-second transport deadline, existing response-size/completion checks. Writer returns only selection replacement text, not a tool plan. Empty AI output is invalid; deletion is the explicit empty manual candidate.

Independent review receives the exact original raw author instruction, current instruction, candidate full body, exact paragraph evidence catalog, effective retrieved context and computed Han count. Evidence IDs and verdict consistency are validated by the existing strict parser. Review starts unverified and only a real successful audit can produce passed/failed. The installed runtime 4000-Han minimum is retained as a separate local failure; the actual independent verdict is retained in independent_result without alteration. Network, validation and cancellation failures preserve the previous candidate and show unverified review, never fabricated pass. Old raw reports remain in bounded model_records.

## Annotation response

Public fields: id, project_id, chapter_id, source `{version_id,body_sha256,start,end,quote}`, original_instruction, instruction, kind, candidate (null if absent; empty string means delete), optional candidate_origin, review, history, status, created_at, updated_at, job, pending_intent; optional prepared_request, model_records, acceptance, undo, reconciliation. `stale` is computed from current chapter version/hash/activity. Persisted source_body, internal model_request and candidate_history are not returned. With a candidate, preview is `{before,after,before_sha256,after_sha256,replacement}`; before/after are full exact bodies. History contains action, operation_id, at, instruction, candidate_sha256. Main status is open, accepted, undone, discarded, or projected needs_confirmation.

Review fields: status unverified/passed/failed, passed null/boolean, optional issues, independent_result, candidate_sha256, body_sha256, reviewer metadata, timestamp/local findings/error. Acceptance snapshots the real review and review_choice separately. model_records retain at most 20 attempts, with response text capped at 32,000 characters, full-response hash and truncation flag; no credentials/headers are stored. Candidate history is capped at 20 retained versions. Latest request/context only is retained. Limit exhaustion requires a new annotation rather than hidden eviction. GET list currently includes full previews and is not paginated.

## Commit uncertainty and undo

Before NovelService.execute('save_chapter'), persist a pending metadata intent with operation ID, exact before version/hash, after hash and expected revision. Body changes use the established business-save/version-history path, never SQL payload edits. A failure during body save or final metadata receipt leaves the durable intent. GET projects status needs_confirmation and reconciliation `{observed:{version_id,body_sha256},matches_before,matches_after,automatic_replay:false}`. Do not interpret HTTP success alone as body success: inspect annotation.status and pending_intent.

POST reconcile with confirmed true and exact observed version/hash. resolution `not-applied` clears the pending intent only if current version/hash equal the intent's before state. resolution `applied` requires exact after hash, a different current version, and the immediate chapter-version predecessor matching before; it finalizes metadata only. Ambiguous histories reject and require author/coordinator intervention; never silently replay or overwrite. After not-applied reconciliation, a new operation can be explicitly attempted. Undo requires the current accepted after-version AND after-hash, rejecting even identical content saved as a later version. Later edits are never discarded.

## Persistence, errors and integration limitations

Sidecar: sibling `<workspace-database-filename>.chapter-annotations.sqlite3`, like ReviewBatchStore, with independent SQLite transactions. Preserve the sidecar with normal whole-profile/library directory copies; standalone workspace JSON exports/backups and project remapping do NOT include annotation metadata. Dedicated sidecar export/import/remapping integration is not implemented. No workspace schema keys or version upgrade are introduced. No private profiles, novels, databases, logs, credentials or providers were accessed during development.

Existing HTTP mappings: POST invalid input is 422, conflict is 409, missing project/annotation is 404, storage failure is 500. GET uses the existing server read-error mapping. Commit ambiguity instead returns the annotation needs_confirmation projection and must be handled explicitly. Discard is a tombstone, not physical deletion. Cancel cannot refund a provider request already submitted. Interrupted jobs are displayed interrupted and are never restarted automatically.

Concurrency: annotation mutation ownership is per-annotation; model jobs and body acceptance/undo claim the existing shared task execution slot. Existing ChatAgent and console/generation-task statuses are checked for conflicts. Metadata transactions never span remote requests or whole-workspace body saves. ChatAgent does not itself use the shared execution slot: a concurrently starting chat task is detected by subsequent guards/revision checks, but cross-producer admission is not a single atomic book lease. Multi-server/multi-process sidecar ownership is not implemented; run a single LocalServer per profile. These admission limitations require coordinator review before claiming strict global serialization. Model response publication is guarded immediately before storing but is not atomically coupled to workspace revision; a simultaneous later edit is exposed as stale and can never be accepted against the old source.

Transport limitation: this first backend explicitly rejects SSE connections and non-default native Chat token/temperature profiles rather than silently ignoring their settings. Supported JSON protocols reuse the existing ChatAgent transport. Destination display/frozen messages describe the logical request; provider-specific wire serialization follows existing transport rules. No frontend work, automated tests/E2E, run_checks, real model requests or build were executed as instructed. Coordinator must review, integrate/build, and resolve remaining admission/backup requirements before production release.
